# 源码瘦身与拆分准备（2026-10-22）

## 范围与判断方法

本轮对初始检出的 900 个受版本管理文件建立静态清单，读取源码、测试、配置和文档引用；解析全部 676 个 Python 文件，统计函数职责与导入关系。后端包含 262 个生产模块、275 个测试文件，共 142,470 行生产 Python。前端覆盖 JS 模块入口、全局事件桥、CSS 导入、构建、单元测试及浏览器测试入口。

静态遍历不等于逐条业务路径均已运行，也不能证明仓库外没有调用者。删除依据结合导入、字符串引用、装饰器注册、动态依赖装配、CLI（命令行入口）和部署调用；保留旧接口的现有外部契约。生成的完整清单和检查日志放在本地忽略目录 `.codex/`，不作为应用源码提交。

## 对抗性复核

以“怎样证明这次删除可能是错的”为出发点复查，针对以下反例：

1. **没有生产导入仍可能有独立用途。** 保留 `*_runner.py`、报表 CLI、数据库迁移、研究/回放能力和故障注入工具；没有仅凭入边为零删除它们。
2. **装饰器和字符串也能调用函数。** HTTP 路由不是死函数；核对 `paper_trading` 的动态依赖字段，删除名单中不含装配字段。
3. **看似重复的测试可能验证不同检查器。** 另外两组 AST（把源码解析成语法结构）检查虽然测试文本相同，但各自使用不同模块的检查器，全部保留。只合并实际重复的 Provider 检查。
4. **删除旧算法测试可能丢失有用约束。** 旧采样辅助函数确实无生产调用，但“数量有上限、输入顺序不影响结果”仍有价值，因此将原测试转向 `_canonical_alpha_frame`，不把它一并丢弃。
5. **留下检查器不代表它还能发现错误。** 在内存中向 Provider 注入写入动作，保留的检查明确失败；随后用真实源码确认检查通过。再把正式采样入口的上限放大到 1,000,000，迁移后的测试也明确失败。两个反例均不落盘、不改真实数据。
6. **大文件和小文件都不能只按大小删除。** 保留提交使用的 `frontend/dist`、第三方图表资源、旧版本 schema 夹具和有职责边界的研究服务/仓储。
7. **旧架构断言可能反过来强制保留死代码。** 全量测试发现周期服务测试要求主文件包含 `PCS.cycle_snapshot`，但真正快照调用位于 `paper_cycle_service.archive_cycle`。同步断言只要求主文件保留实际使用的委托，保留直接快照和归档行为测试；整个周期服务测试模块 12 项复跑通过。
