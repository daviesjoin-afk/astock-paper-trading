# v2.0.0 发布说明 — 从“能跑”升级为“可验证、可回放、可扩展”

发布日期：2026-09-20。功能基线截至 PR #174（merge commit `d754fd4e8ac966a8f0e50f079906aa029c1cb4c0`）。

v2.0.0 是自 v1.3.0 以来的一次平台级升级。重点不是增加更多策略或页面，而是让模拟交易、历史研究、风险决策和学习评估都有更清楚的事实边界：系统现在更强调**当时可知、执行可证、历史可复现、未知不猜测**。

> **仍然是 paper trading only。** 本版本不连接券商、不触碰真实资金，也不提供杠杆、做空或普通股票 T+0 回转。

## 这次升级带来了什么

### 1. 策略从“固定几套”变成可管理、可版本化的平台能力

过去系统更接近固定策略集合；v2.0.0 之后，策略可以作为长期管理的对象存在：

- 可以创建、验证、启用、暂停、退役和归档策略；
- 每次策略修改都会形成不可变版本，历史周期继续使用当时实际运行的版本；
- 浏览器内可以完成策略创建、校验、预览、克隆和生命周期管理；
- 自定义策略使用受约束的声明式规则，不执行任意 Python，也不能绕过系统直接决定最终下单数量；
- 启用或停用策略只影响后续周期，不会静默改写已经运行中的周期。

实际作用是：**现在可以持续迭代策略，同时保留历史可解释性，不会因为今天改了参数而改变昨天“当时到底跑的是什么”。**

### 2. 多策略共享资金时，分配和执行规则更统一

多策略同时运行时，资金、仓位和执行不再由各策略各自处理：

- 多个策略可以共享同一资金池，同时保持独立归因；
- 建仓额度会结合资金规模、风险、持仓上限、相关性和已有敞口统一计算；
- 待成交订单会占用相应容量，过期、撤销或失败后再释放；
- 信号有效期、订单有效期、分阶段入场和重试行为有统一规则；
- 策略只能表达“想买/想卖什么”，最终数量和是否允许成交由系统统一门禁决定。

实际作用是：**策略数量增加后，不会因为各策略各算一套资金和仓位逻辑而出现重复占资、超额敞口或执行规则不一致。**

### 3. “订单显示已成交”不再自动等于真实成交事实

v2.0.0 把模拟成交的真实性要求提高了一层：

- 订单状态和实际可验证成交被明确区分；
- 只有有成交证据的记录才会进入正式收益、NAV 和执行表现统计；
- 延迟成交、重试成交和历史成交都会保留所属周期；
- 升级前无法证明的旧记录不会被强行补成“已验证”。

实际作用是：**收益和持仓不再只相信一个状态字段，而是尽量建立在真正发生过的模拟成交事实之上。**

### 4. 历史研究更严格地遵守“当时可知”

本版本系统性收紧了历史回放和学习中的未来信息泄漏：

- 历史选择、训练和评估都按明确时间边界读取数据；
- 回放使用固定历史时间，不再受运行机器“今天是什么日期”影响；
- 历史股票是否可交易、是否停牌、是否处于风险状态等信息有独立历史记录；
- 能区分“当时不存在”“后来才看到”“上游返回未知/错误”“旧数据无法证明来源”等不同情况；
- 无法证明的历史事实保持 unknown，而不是补成 false、0 或当前值；
- 训练/评估采用防泄漏的时间切分和 walk-forward 方式。

核心原则：

```text
历史时点不知道的事实，后来的数据库也不能替历史“补知道”。
unknown != false != zero
```

实际作用是：**历史结果更接近真正站在当时信息集上做出的决定，而不是被未来数据悄悄“美化”。**

### 5. 持仓、成本、风险和周期归属更一致

v2.0.0 继续收敛“谁才是事实来源”：

- 当前持仓数量和成本以实际模拟成交形成的持仓事实为准；
- 展示层数据不再反过来决定真实持仓；
- 订单、持仓、风险状态和周期之间的归属更加明确；
- 同一股票的新一轮持仓会和上一轮持仓的风险状态分开；
- 历史风控不会因为当前周期、当前日期或后来出现的新候选而改变过去的判断；
- 换仓、席位升级、待买占用和资金预算按同一周期和同一历史时点解释。

实际作用是：**旧周期不会被新周期的数据污染，历史持仓和风控结果也更容易追溯“为什么当时会这样”。**

### 6. 风控从“读当前状态”进一步升级为可回放决策

风险扫描和卖出判断现在更强调确定性：

- 风险扫描有明确的运行状态，可区分执行中、完成、失败和重试；
- 扫描过程中如果周期发生切换，会直接中止旧周期写入，而不是继续混写；
- 风险判断使用明确的历史日期和持仓来源；
- 对持仓质量的复核会追溯到实际开仓订单和对应信号，而不是拿“最新信号”替代；
- 找不到可靠来源时保持 unknown，不自动换成当前策略或最新数据；
- 历史换仓只允许使用当时已经出现的候选和评估结果。

实际作用是：**风险结果不再依赖“现在数据库里最新是什么”，同一份历史事实应得到同一类判断。**

### 7. 自进化与 AI 更像“受控研究流程”，而不是自动改交易系统

自进化能力在 v2.0.0 中加入了更严格的评估和晋级边界：

- 新参数或新版本先作为 challenger 进行影子评估；
- 候选通过验证不等于立即获得正式执行权；
- 风险参数变化需要额外门禁，不能因为学习结果自动放宽保护；
- AI reviewer 的失败、分歧和正常持有被区分记录；
- AI/Adaptive 仍然停留在建议、评估和 shadow 范围，不直接取得下单权限。

实际作用是：**系统可以继续学习和比较新策略，但学习结果不会绕过既有交易与风控边界。**

### 8. Web 操作和写接口更安全

本版本同步加强了日常使用体验和运行安全：

- 策略创建和管理集中到统一工作台；
- 关键页面流程增加自动化浏览器测试；
- 所有修改系统状态的 HTTP 请求统一经过 operator 安全边界；
- 默认本地模式只允许本机访问写接口；
- 如果配置访问令牌，则所有写请求都要求有效 Bearer token；
- 配置错误时选择 fail closed，而不是静默放行；
- 安全泄漏扫描继续作为 CI 强制门禁。

实际作用是：**本地使用更直接，对外部署时也不再把“点一下确认”误当成真正的访问控制。**

## 需要注意的行为变化

### 策略范围

不要再假设系统只有固定的五套策略。内置策略是模板和历史基线，实际参与某个周期的策略以该周期开始时确定的快照为准。

### 历史成交

旧数据中的“filled”不一定会被视为已验证成交。没有足够证据的历史记录会保留为 unknown，而不是强行计入正式绩效。

### 历史数据

升级不会给无法证明的旧数据伪造来源、时间或周期归属。无法可靠重建的内容会明确保留为空或 unknown。

### 写接口安全

- 未配置 operator token：写操作仅允许本地访问；
- 配置了合法 token：包括 localhost 在内的写请求都必须携带 Bearer token；
- token 配置非法：写请求直接拒绝；
- 对外暴露服务时仍应同时使用 TLS、网络访问控制和正确的反向代理配置。

## 数据库升级

v2.0.0 的正式迁移链为：

- paper trading 数据：v21
- adaptive learning 数据：v1

升级会按顺序执行迁移，并在首次实际迁移前创建一致性备份。对于无法证明的旧历史事实，不做猜测性补全。

推荐先执行：

```bash
python backend/db_migrate.py all --dry-run
python backend/db_migrate.py all
```

## 升级建议

1. 停止 scheduler / cron / 其他写入进程；
2. 备份模拟盘数据库、学习数据库和自定义策略配置；
3. 拉取 v2.0.0；
4. 执行 migration dry-run；
5. 正式迁移；
6. 如需远程写访问，配置 operator token；
7. 重建前端或容器；
8. 检查版本号、健康状态、当前周期、策略状态和账户数据；
9. 确认无异常后再恢复 scheduler。

Docker：

```bash
docker compose down
docker compose up -d --build
```

本地 Python：

```bash
python -m pip install -r requirements.lock
python backend/db_migrate.py all
python -m uvicorn backend.main:app --port 8600
```

## 已知边界

- 仅用于 paper trading，不连接券商或真实资金；
- 无法证明的历史事实会保持 unknown；
- 全链路 deterministic replay 仍在继续完善，目前已有 point-in-time、候选追踪和局部确定性基础；
- 核心交易编排仍在持续模块化，但现有外部使用方式保持兼容；
- Adaptive / AI 不直接拥有交易执行权限。

## 一句话总结

v2.0.0 的核心变化不是“多了多少功能”，而是：

> **策略可以持续迭代，交易事实可以验证，历史研究尽量只使用当时可知的信息，风险结果可以追溯，未知数据不会被系统擅自猜成确定答案。**
