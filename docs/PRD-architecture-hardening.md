# PRD：架构硬化与 OSS 可维护性治理

**状态**：草案，待评审
**日期**：2026-09-03
**项目**：`daviesjoin-afk/astock-paper-trading`
**本地基线**：`master` / `c9add450`（以本地实际提交为准）
**产品边界**：仅限 A 股模拟交易，不接入真实券商下单。

## 1. 背景与问题

最近的架构审计指出，项目的交易规则、风控、数据核验和并发控制已有较好基础，但核心代码和工程边界开始影响维护性。主要问题包括：

1. `backend/paper_trading.py` 同时承担持久化、账户、订单、成交、风控、调度、租约和审计等职责，形成巨型模块（God Object，指一个模块承担过多不相关职责）。
2. `backend/db_migrate.py` 与运行时 `ALTER TABLE` 可能形成两套数据库演进真相源。
3. API 的 `confirmed=true` 只是界面防误触，不是身份认证；服务若绑定公网地址，写接口边界不清晰。
4. 活跃、历史、影子和实验策略缺少统一注册表，文档、API 和 adaptive 展示可能语义漂移。
5. `decision_engine.py` 仍可能自行读取缓存或联网，难以做到确定性回放（同一输入得到同一决策）。
6. `data_fetcher.py`、`adaptive_engine.py` 和前端单文件的职责与历史镜像偏多，扩展入口不够清楚。
7. CI、依赖版本和 `master` 分支保护尚未覆盖完整的 OSS 维护闭环。

上述文件大小、调用关系和远端设置在实施前必须由本地基线重新核验；审计文字是需求输入，不直接视为已验证事实。

## 2. 目标

- 在不改变现有模拟交易规则和公开 API 行为的前提下，建立可渐进拆分的架构边界。
- 让数据库迁移可版本化、可回滚、可对旧库做回归验证。
- 让决策层只依赖显式证据输入，支持回放、测试和替换行情提供方。
- 明确本机模式与服务器模式的安全边界。
- 保证 adaptive 子系统只能读数据、不能依赖订单执行路径。
- 形成可被其他贡献者理解和验证的架构文档、CI 和测试证据。
- 采用“本地先验证 → 服务器再验证 → 最后才推送 GitHub”的交付流程。

## 3. 非目标

- 不新增交易策略、AI 能力或真实交易能力。
- 不在本阶段大规模改写交易状态机或更换前端框架。
- 不为了整理代码删除用户已有数据、历史迁移、Git 历史或正在进行的 PR。
- 不在服务器测试未通过或证据不完整时推送 GitHub、合并 PR 或修改生产分支保护。

## 4. 交付闸门与工作流

### 4.1 本地阶段（L）

- 工作目录：本地独立分支，不能混入现有 PR #4 的测试修复。
- 允许：阅读、实现、运行测试、生成本地文档和提交本地 commit。
- 禁止：推送 GitHub、修改远端仓库、部署服务器、接入真实券商。
- 通过条件：本地验收清单全部通过，且变更可回滚。

### 4.2 服务器阶段（S）

- 仅在 L 阶段通过后执行部署或同步；本次目标为 **2026-09-03 完成本地版本推送到服务器**。
- 服务器验证日期：**2026-09-04**（明天）；实际以用户开始测试的时间为准。
- 服务器测试前必须保留数据库和当前版本回滚点。
- 服务器阶段只验证已通过本地测试的同一版本，不临时加入未验证改动。
- 若服务器测试失败、结果不完整或无法确认进程/HTTP/数据库状态：立即停止，不进入 GitHub 阶段。

### 4.3 GitHub 阶段（G）

- 只有服务器测试明确通过，并得到用户确认后，才允许 push 分支或创建/更新 PR。
- push、PR 创建、CI 通过、合并和部署分别报告，不能把“已准备”描述成“已完成”。
- 本 PRD 当前不执行任何 GitHub 写操作。

## 5. 功能与架构需求

### P0：仓库与安全边界硬化

1. 新增 `ARCHITECTURE.md`，说明 API → Service → Domain 的依赖方向、模块职责和禁止依赖。
2. 新增 `SECURITY.md`，明确 paper-only 边界、敏感配置处理、问题报告方式和本机/服务器运行差异。
3. 本机模式默认只绑定 `127.0.0.1`；服务器模式必须显式开启，并为写接口提供 operator token 或等价会话认证。
4. `confirmed=true` 继续作为防误触字段，但文档和代码中不得将其当作鉴权。
5. 对启动、停止、健康检查和残留进程增加可重复的本地 smoke 验证（smoke test，指最小可运行冒烟检查）。
6. CI 第一阶段至少覆盖单元测试、Python 编译检查、前端语法检查和 Docker 构建/健康冒烟；不因 CI 改造改变交易逻辑。

### P1：数据库迁移单一真相源

1. 所有 schema 演进统一进入有序、带版本号的 migration；禁止业务运行路径隐式执行新的 `ALTER TABLE`。
2. migration 必须支持事务、重复执行保护、失败回滚和当前版本检查。
3. 建立 repository（仓储层，指隔离数据库读写的接口）边界，先覆盖账户、订单、成交、持仓和周期等高频对象。
4. 为至少一个旧 schema fixture 建立“旧库 → 最新库”的回归测试，并校验关键数据不丢失。
5. 迁移失败时必须保留原库备份或可恢复副本；不允许无备份的破坏性迁移。

### P2：数据与纯决策层

1. 将行情服务、缓存、健康状态、重试和 Eastmoney/Tencent/Sina provider 拆成明确接口。
2. 统一行情输出的代码、价格、时间戳、来源、新鲜度和核验状态。
3. `decision_engine` 只接受不可变的 `DecisionContext`/`EvidenceSnapshot`，不得在决策函数内联网、读 SQLite 或读磁盘。
4. 缺失或过期证据继续遵循现有 fail-closed（证据不足时拒绝交易）规则。
5. 增加同一输入的确定性回放测试，确保拆分不改变现有决策结果。

### P3：交易核心渐进拆分

1. 采用绞杀式拆分（先抽出新模块，再逐步切换调用）而不是一次性重写 `paper_trading.py`。
2. 建议顺序：Execution → Portfolio → Risk → Slot/Scheduler Orchestrator。
3. 每次拆分保持现有 API、数据库字段语义和审计事件兼容。
4. 每完成一个边界，必须运行完整回归测试和关键 replay/invariant（不变量）测试。
5. 未有等价测试覆盖的旧逻辑不得删除。

### P4：策略注册与 adaptive 隔离

1. 建立唯一 strategy registry，至少支持 `active`、`legacy`、`shadow`、`deprecated` 状态及策略版本。
2. README、API、数据库记录、market policy 和 adaptive 展示均从 registry 获取策略身份。
3. adaptive 模块只能通过只读数据端口获取行情/账本信息，禁止直接 import 订单执行模块。
4. 保留并自动化校验“adaptive 永不提交订单”和“不能自动放宽风控”的架构不变量。

### P5：前端、CI 与依赖治理

1. 先确定一个前端 source of truth，历史 JS/CSS 镜像只保留在 Git 历史，不继续作为运行时文件。
2. 在不引入重型框架的前提下，按原生 ES module 拆分 API、状态、paper、risk、adaptive 和组件。
3. CI 逐步加入 lint、覆盖率、依赖审计和 Docker health smoke，并保留现有 Python 3.11/3.12 兼容验证。
4. 评估 `requirements.in` + lock 或 `pyproject.toml` + `uv.lock`，确保同一 commit 可复现安装。
5. `master` 分支保护、必需 CI、禁止强推/删除作为 GitHub 阶段单独评审项；本 PRD 不在服务器测试前自动修改远端设置。

## 6. 本地验收标准

以下项目全部通过，才允许进入服务器阶段：

- 现有 `backend` 测试全部通过（当前基线为 123 个测试，以实际运行结果为准）。
- `ResourceWarning`、Python compile、前端 `node --check` 均无新增错误。
- 启动后 `/api/health` 与首页返回 200；停止后端口释放且无残留服务进程。
- migration 旧库回归、重复执行、失败回滚和关键字段保真测试通过。
- 本机默认绑定地址为回环地址；写接口未认证时按设计拒绝，读接口行为符合文档。
- adaptive 静态依赖检查和运行时测试均证明不会触发订单提交。
- 关键交易规则、风控门禁、租约/fencing、审计和 replay 测试与基线结果一致。
- 变更范围、备份点、回滚命令和测试输出均记录在开发记录中。

## 7. 服务器验收标准（2026-09-04）

- 今天部署的是本地验收通过的同一 commit，部署前有可验证的数据库备份和回滚点。
- `/api/health`、首页和关键只读 API 返回预期状态；启动/停止不会遗留旧进程。
- 端口由预期进程持有，日志无迁移、认证、数据库锁或调度异常。
- 运行一次最小模拟周期/只读检查，确认无重复执行、无越权写入、无真实券商调用。
- 明天服务器测试失败或无法取得完整证据时，状态标记为“服务器未通过”，不得 push GitHub。
- 服务器通过后，先由用户确认，再进入 GitHub 阶段。

## 8. 风险与回滚

| 风险 | 预防 | 回滚 |
| --- | --- | --- |
| 拆分改变交易语义 | 保留旧入口、逐步切换、全量回归 | 切回上一 commit/旧入口 |
| 旧 SQLite 迁移失败 | 备份、fixture、事务和失败演练 | 恢复备份并停留在旧版本 |
| API 暴露导致未授权写入 | 本机默认回环绑定，服务器写接口认证 | 关闭写接口/恢复旧配置 |
| adaptive 依赖越界 | 静态 import 检查和运行时不变量 | 禁用 adaptive 任务 |
| 前端镜像漂移 | 单一 source of truth 和构建校验 | 恢复上一构建产物 |

## 9. 完成定义（Definition of Done）

本项目必须分别记录以下状态，不合并表述：

1. **本地完成**：代码/文档完成，测试和回滚证据齐全。
2. **服务器完成**：同一版本已部署，2026-09-04 测试明确通过。
3. **GitHub 完成**：仅在服务器通过且用户确认后，分支已 push、PR 已创建/更新、CI 结果已记录。

本 PRD 完成的当前定义是：文档已写入本地仓库，三道闸门和验收标准明确；不代表代码已修改、服务器已部署或 GitHub 已推送。
