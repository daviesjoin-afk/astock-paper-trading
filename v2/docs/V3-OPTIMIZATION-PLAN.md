# AStock V3 优化方案（2026-11-11 草案）

> 一句话：新 V2 不是"写得差"，是**为了纯净把三层能力砍光了**——入口从 40+ 缩到 7 个、
> 标的从全市场缩到 2 只、决策从"治理过的策略库"缩成"一条写死的均线规则"。
> V3 要做的不是加功能，是**把砍掉的能力按模块化重新长回来，并且把进化的判据做实**。

本文包含：现状诊断、目标拆解、可借鉴轮子清单、目标架构、多级菜单信息架构、
数据层重建、自进化设计、性能设计、分阶段落地、明确不做的事。

---

## 决策记录（2026-11-11 定稿）

| # | 议题 | 决定 | 备注 |
| --- | --- | --- | --- |
| 1 | 数据校验 | **不做独立自检系统**。以收益波动曲线为唯一验收标准 | 见 6.5 节：异常波动在曲线上天然可见，不额外建检查层 |

| 4 | 单一验收标准 | **能挣钱就是好的** | 所有设计围绕"让曲线好看且真实" |

## 0. 结论先行

| 问题 | 现状 | V3 怎么办 |
| --- | --- | --- |
| 简陋 | 7 个 API、5 个页面块、2 只股票 | 全市场 5000+ 标的，40+ 端点，6 大模块 20+ 子页 |
| 数据 | 手工指定 symbols，2.7MB 级 JSON 手工发布 | 通达信盘后包一次拉全市场，落 SQLite/Parquet，自动校验 |
| 自进化 | 只调两个槽位的现金预算 | 策略库 + shadow 验证 + 晋升/回滚治理（回收旧 v2 `evolution.rs`） |
| 反应速度 | 收盘价 + 手工点"推进" | 收盘后自动跑完整链路；盘中快照扫描可选 |
| 前端 | 414 行无路由无框架 | 真路由 + 组件库 + 多级菜单 + 虚拟滚动表格 |
| 可复用 | 旧 v2 的 calendar/instrument/evolution 被删了但还在 git | `git checkout HEAD --` 直接回收，别重写 |

**最大的一个判断**：数据层是瓶颈。现在的"完整矩形 JSON + 手工审核发布"模型在
5000 只股票规模下必然崩（估 100MB+ 单文件、每天全量重写）。这一层必须换掉，
否则上面加多少功能都是空中楼阁。

## 1. 现状诊断：为什么会觉得简陋

### 1.1 数字对比

| 维度 | V1（Python） | 旧 V2（schema 15） | 新 V2（schema 2） |
| --- | --- | --- | --- |
| 后端模块 | 778 个 .py | 18 个 domain + 2 store | 7 个 domain + 1 store |
| HTTP 端点 | 大量 | 40+ | **7** |
| 前端 | 3132 行 + 7 个 feature 模块 | 单文件 | 414 行 |
| 一级菜单 | 5 | 5 | **1（就一张卡）** |
| 二级/三级菜单 | 7 + 8 + 7 | 有 | **0** |
| 标的覆盖 | 全市场 | 少量 | **2 只** |
| 策略数 | 多策略 + 克隆 + 版本 | 2 槽 | 2 槽硬编码 |

### 1.2 三层缩水，各有各的性质

**第一层：入口缩水（该骂）**
新 V2 只剩 `health / account / run / positions / trades / rebalances / coverage`。
连"账户净值曲线"、"单日盈亏归因"、"持仓浮盈浮亏"这类最基础的东西都没有。
这不是"精简"，是**产品没做完**。

**第二层：数据缩水（是设计选择，但选错了）**
新 V2 引入"reviewed 价格集合、完整矩形、人工审核"这套机制，动机是对的（不允许
猜价格、不允许未来函数），但**执行方式把规模锁死了**：一次只审 2 只股票、一次只发
一个窗口、人工 `--review` 确认。这是"审计脚本"的形态，不是"行情系统"的形态。

**第三层：决策缩水（最伤）**
- 稳健：20 日均线 > 60 日均线 且 波动率 < 中位数
- 激进：5 日动量为正 且 突破 20 日高点

就这两条。而且**不可参数化、不可替换、不可并存**。用户眼里的"简陋"主要来自这里：
打开系统，能做的事情是"输本金、点一下、看两张卡"，没有任何可探索空间。

### 1.3 旧 V2 里被埋掉的资产（可白捡）

这些文件在 `HEAD` 里还在，工作区被删了，**一句 `git checkout HEAD -- <path>` 就能回收**：

| 文件 | 行数 | 价值 | 判断 |
| --- | --- | --- | --- |
| `domain/calendar.rs` + `data/calendar-2026-v1.json` | 155 | 沪深 2026 交易日历，带 SSE/SZSE 公告号与 URL | **直接收**，现在完全靠"数据里有什么日子"推断，脆弱 |
| `domain/instrument.rs` + `data/instruments-offline-v2.json` | 142 | 标的身份 + 整手规则，带证券法条款 locator + sha256 | **直接收**，现在整手规则硬编码在 account.rs |
| `domain/evolution.rs` | 168 | 晋升/回滚治理：最小 OOS 天数、最小 shadow 天数、回撤帽、晋升边际 | **改造后收**，这才是"自进化"的真骨架 |
| `domain/exposure.rs` | 132 | 敞口计算与上限 | 收，选股/IPU 要用 |
| `domain/portfolio.rs` | 78 | 组合聚合 | 收，净值曲线要用 |
| `domain/digest.rs` | 96 | 内容摘要（sha256 规范化） | 收，审计链要用 |

旧 V2 的问题不是模块不好，是**模块之间耦合成了"实验-比较-研究"的迷宫**，
而且对外暴露成一堆需要先理解概念才能用的端点。V3 要保留这些零件，扔掉那套叙事。

## 2. 四个目标翻译成工程语言

用户说的四个词，落到代码上分别是：

### 2.1 "快速响应"

拆成三个不同的指标，别混为一谈：

| 层次 | 指标 | 现状 | 手段 |
| --- | --- | --- | --- |
| 接口延迟 | p99 < 50ms | 每次请求新建 SQLite 连接 | 连接池 + 预编译语句 + 只读副本 |
| 页面首屏 | < 800ms | 全量拉 `/v2/account`（含全部成交） | 分层端点 + 分页 + 前端缓存 |
| 全市场扫描 | 5000 只 × 250 日 < 3s | 不存在 | 列存 + 向量化 + rayon |

**真正的"反应快"是第四件事**：收盘后多久能把当天数据变成可交易信号。现在这个链路是
"人工取数 → 人工审核 → 手工发布 → 手工点推进"，小时级。V3 目标：**收盘后 5 分钟内自动完成**。

### 2.2 "模块化扁平化"

不是"目录越浅越好"，是两条硬规则：

1. **依赖单向**：`http → service → domain ← store`，domain 零 IO、零时钟、零网络
2. **新增一个策略 = 新增一个文件 + 一行注册**，不改任何已有文件

第 2 条是判据。做不到，就不是模块化。

### 2.3 "自动运行"

不是"加个 cron"，是**幂等 + 可重入 + 失败可诊断**：

- 同一天跑两次，结果必须完全一致（现在 `day_run` 表已经保证了，好）
- 中途崩了，重跑能从断点接上（现在事务边界是整天，好）
- 失败了要能立刻说清"哪一步、为什么"（现在只有裸 500，要补）
- 数据没到，要"明确拒绝"而不是"用旧数据凑"（现在已经是这样，好，保持）

### 2.4 "自主进化"

这是最容易做成玩具的一环。必须先定死**什么叫进化成功**：

> 一个策略只有在**样本外**（out-of-sample）和**影子期**（shadow，真跑但不真下单）
> 都满足硬阈值，且有明确证据链，才能被晋升到实盘槽位。任何一个偏小的回测结果都不算。

旧 V2 的 `evolution.rs` 定义的默认阈值可以直接用：
`min_out_of_sample_days=20, min_shadow_days=10, min_trades=10, max_drawdown_bps=1500,
promote_margin_bps=50, rollback_drawdown_bps=2000`。

这组数字不完美，但它是**一个诚实的起点**：它保证"单次幸运回测无法晋升"。

## 3. 拿来主义清单（不重复造轮子）

用户特别要求这一节。原则：**能借思路就借思路，能借代码就借代码，但绝不为了用而用**。

### 3.1 数据层 —— 必接

**`simonlin1212/a-stock-data` v3.10.4**（Apache-2.0，已在本仓库 `.staging/`）
- 现在只用了它的腾讯日线 + 通达信盘后包 + 新浪复权因子三个入口
- 还有 **84 个端点没用**，其中 V3 该立刻用上的：

| 端点 | 用在哪儿 | 为什么关键 |
| --- | --- | --- |
| §1.3 通达信盘后包 | **每日全市场截面** | 一次 2.7MB 拿沪深北全部证券开高低收+量额，这是解掉"只有 2 只股票"的钥匙 |
| §12 深交所交易日历 | 自动推进的日期来源 | 现在靠推断，有了官方日历才能安全自动跑 |
| §1.1 腾讯实时快照 | 盘中看板 | PE/PB/市值/换手/涨跌停，一个请求批量 |
| §1.6 新浪复权因子 | 除权检测 | 现在只是"疑似提示"，要升级成自动拒绝 + 自动重取 |
| §6.5 baostock 估值历史 | 估值因子 | PE/PB 分位数是最稳的 A 股因子之一 |
| §3.3 东财 slist | 行业/概念归属 | 板块轮动策略的前提 |
| §3.7/3.8 行业与板块资金流 | 资金面因子 | 日频，东财独有 |
| §14 事件驱动 | 风险过滤 | 业绩预告/减持/质押，用来**排除**而不是**买入** |
| §6.8 ST 名单 | 风控黑名单 | 稳健策略绝不该买 ST |

- 二进制布局解析参考 `jing2uo/tdx2db`（MIT），a-stock-data 已经内嵌移植好了，直接用。

**关键改造**：把 a-stock-data 从"我要 fetch 哪 2 只"改成"每天拉全量包落库"。
Python 侧只做**抓取 + 交叉核对 + 落库**，不参与任何交易决策。

### 3.2 回测/事件驱动 —— 借架构不借依赖

| 项目 | 语言 | 借什么 | 不借什么 |
| --- | --- | --- | --- |
| [`nautilus_trader`](https://github.com/nautechsystems/nautilus_trader) | Rust+Python | 事件驱动分层（Data→Strategy→Risk→Execution→Portfolio）、同一份策略代码在回测与实盘语义一致 | 整个框架。太重，且面向多资产多交易所，我们只有 A 股股票 |
| [`barter-rs`](https://github.com/barter-rs/barter-rs) | Rust | 纯 Rust 事件总线 + 状态管理 + 指标库的设计取舍 | 它的 exchange 适配器层 |
| [`QuantConnect/Lean`](https://github.com/QuantConnect/Lean) | C# | 算法框架的 `OnData/OnBar` 生命周期划分 | 一切实现 |

**具体到我们要抄的一个点**：nautilus 的"**同一份策略代码，回测与实盘零差异**"。
这一条如果做到，就永远不会有"回测赚钱实盘亏"的经典坑。做法是：
策略只输出 `Vec<OrderIntent>`，回测和实盘共用同一个 `ExecutionModel` trait，
只在"价格从哪来"和"时间怎么走"上换实现（同 crate 不同 feature）。

### 3.3 因子与表达式 —— 借设计

| 项目 | 借什么 |
| --- | --- |
| [`microsoft/qlib`](https://github.com/microsoft/qlib) | **因子表达式 DSL** 的思路：`Ref($close,1)/$close-1` 这种写法让因子可配置、可序列化、可缓存。它的 `Expression` + `ExpressionCache` 设计值得照抄概念 |
| `qlib` 的 `Alpha158` | 158 个已验证的 A 股因子清单，直接拿来当初始因子库 |
| [`vectorbt`](https://github.com/polakowo/vectorbt) | 向量化回测的参数网格思路（我们不需要它，但"一次算 1000 组参数"的性能意识要有） |

**注意**：不要引入 qlib（Python 依赖地狱）。只借**因子表达式的语法设计**，
用 Rust 写一个 200 行的小求值器就够。

### 3.4 前端 —— 借组件不借框架

| 需要 | 现成方案 | 建议 |
| --- | --- | --- |
| 路由（多级菜单前提） | `@tanstack/router` 或手写 hash 路由 | **手写**。我们只有 ~25 个页面，引入 router 反而是负担。但必须有：URL 可分享、刷新不丢状态、面包屑 |
| 表格（5000 行持仓/候选） | `@tanstack/table` + 虚拟滚动 | **引入** `@tanstack/virtual`。手写虚拟滚动必踩坑 |
| 图表（K 线、净值曲线） | `lightweight-charts` (TradingView, Apache-2.0) | **引入**。v1 用的 echarts 太笨重，K 线专用库体积小得多 |
| UI 组件 | `shadcn/ui` 不方便（React 依赖） | 保持现状的自写 CSS。v1 的 `console-v5.css` 设计语言可以复用 |

**一个提醒**：v1 前端是 3132 行单文件，这是它后来难维护的根因。V3 从第一天就要
"一个页面一个文件 + 一个 feature 一个目录"，别再走回头路。

### 3.5 运维与可观测 —— 借工具

| 需要 | 方案 |
| --- | --- |
| 结构化日志 | `tracing` + `tracing-subscriber`（现在用的是 `eprintln` 级别） |
| 指标 | `metrics` crate + 一个 `/metrics` 端点暴露 Prometheus 格式 |
| 鉴权 | 最简单够用：一个 `ASTOCK_TOKEN` 环境变量 + Bearer 校验中间件。**必须做**，现在 8600 全裸 |
| 部署 | 保持 systemd + nginx，但把 `daily_auto.sh` 提升成 `astock-cli daily` 子命令（Rust 内实现，不依赖脚本） |

### 4.3 关键 trait 设计（决定扩展性）

```rust
/// 策略只输出意图，不知道价格从哪来、怎么成交。
pub trait Strategy: Send + Sync {
    fn id(&self) -> StrategyId;
    fn params(&self) -> serde_json::Value;
    /// 输入当日全市场截面 + 自己的持仓，输出买入/卖出意图。
    fn on_bar(&self, ctx: &BarContext) -> Vec<OrderIntent>;
}

/// 回测与实盘只在这一层分叉。
pub trait ExecutionModel {
    fn fill(&self, intent: &OrderIntent, ctx: &FillContext) -> Option<Fill>;
}
```

有了这两个 trait，"加一个策略"就真的只是加一个文件。这就是 2.2 节说的判据。

## 5. 多级菜单信息架构

V1 的 5×N 结构方向对，但子项太"内部黑话"（"运行策略/策略证据/组合计划工作台"）。
V3 按**用户此刻想干什么**重排：

```
① 总览   Overview
   ├─ 驾驶舱        净值曲线 · 今日盈亏 · 仓位 · 告警
   ├─ 今日信号      今天扫出了什么 · 为什么买/不买
   └─ 运行状态      数据新鲜度 · 最后推进日 · 任务健康

② 行情   Market
   ├─ 全市场         5000 只可排序表格（涨跌幅/量/换手/PE）
   ├─ 个股详情       K线 · 分时 · 基本面 · 所属板块 · 资金流
   ├─ 板块与概念     行业/概念涨跌 · 资金流 · 龙头
   └─ 数据健康      覆盖区间 · 缺格告警 · 交叉核对结果

③ 研究   Research
   ├─ 因子库         因子列表 · 分位 · IC/IR
   ├─ 选股器         条件组合 → 候选池（可保存为策略草稿）
   ├─ 回测           参数网格 · walk-forward · 结果对比
   └─ 候选池         待观察标的 · 加入时间 · 后续表现

④ 交易   Trading
   ├─ 账户           本金 · 总资产 · 两槽权重 · 净值
   ├─ 持仓           数量 · 成本 · 现价 · 浮盈 · 可卖(T+1)
   ├─ 委托与成交     按日/策略筛选
   ├─ 调仓记录       每次预算调整的前后权重与理由
```

## 6. 数据层重建（核心，优先级最高）

### 6.1 现在的模型为什么撑不住

现有 `PriceSet` 是"完整矩形"：声明的每只股票 × 每个交易日都必须有价格，缺一格整批拒绝。

- 2 只 × 65 日 = 130 个点 → 25KB JSON，很合理
- 5000 只 × 250 日 = **125 万个点** → 估 200MB+ 单文件，且每加一天就要重写整个文件
- 而且"完整矩形"这个约束在全市场尺度下是**不可能满足**的：新股上市、退市、长期停牌每天都有

所以：**矩形约束本身不是错，错在把它当成唯一的存储格式。**

### 6.2 目标模型：两张表，不建质量层

```
bar 表（SQLite，可变，日常写入）
  symbol | day | open | high | low | close | prev_close | volume | amount
  UNIQUE(symbol, day)          -- 缺就是缺，允许新股/退市/停牌
  索引 (day), (symbol, day)

audit（不可变，按日冻结，仅留证据）
  audit/<day>/manifest.json    -- 当日入库代码数、数据包 sha256、来源
```

**关键变化**：从"整批要么全对要么全错"改成"逐条入库"。这样能容纳 5000 只，
新股、退市、长期停牌都不会让整批失败。

**不建 `bar_quality` 表，不做独立自检系统** —— 见 6.5。

### 6.3 摄取链路（收盘后自动）

```
17:00  通达信盘后包发布（实测多数在 17:00 前）
  │
  ├─▶ [1] 拉取 g4day/{ymd}.zip  (2.7MB, 沪深北全市场)
  │
  ├─▶ [2] 解析 → 逐条入库 bar 表（含 prev_close，包内自带）
  │
  ├─▶ [3] 写 audit/<day>/manifest.json（不可变证据）
  │
  └─▶ [4] 触发 astock-cli daily（幂等）
```

不做抽样交叉核对、不做多源对账、不做人工 `--review`。
数据进得来就进，进不来当天就空着，第二天能补。

### 6.4 存储量估算（证明 SQLite 够用）

- 5000 只 × 250 日 × 9 列 ≈ 1100 万行
- SQLite 单行 ~60 字节 + 索引 ~20 字节 → **约 1GB**
- 服务器磁盘 193G 用了 38G，完全够
- 查询"某日全市场截面"：`WHERE day = ?` 走索引，5000 行，**< 10ms**

不需要 Parquet、不需要 DuckDB、不需要 Polars。**SQLite 就够，别过度设计。**

如果将来要做 10 年回测（250 万行级别），再加一列存副本也不迟。

### 6.5 关于"不做自检"这条决定的诚实记录

**决定**：不建独立的质量层、不做多源对账、不做抽样交叉核对。以收益波动曲线为验收标准。

**为什么这个决定在大多数时候是对的**：数据出错会直接在曲线上体现成一根异常的柱子。
你每天看一次曲线，异常一眼就能看见。专门建一套自检系统，是为了**提前**发现，
但对个人模拟盘来说，事后看见也来得及——修正数据、重算那天、曲线复原。

**但有一类错误曲线看不出来，必须写在这里**：除权除息。

> 举例：某只股票 10 派 5 元，除权日价格从 10.00 跌到 9.50。
> 系统把它当成"跌了 5%"，触发止损卖出，记一笔亏损。
> 曲线上一根向下的柱子，看着像正常波动，**但它其实是假亏损**。
> 如果不检测，这类错误每天都会累积，最后曲线会系统性偏低——
> 而你会以为"策略不行"，其实是数据在骗你。

**所以这里加一条，成本几乎为零，我建议无论如何都保留**：

通达信盘后包**自带 `prev_close` 字段**（数据源解析代码里已经在读了，`a_stock_data.py:477`）。
所以每天入库时多存一列，然后：

```sql
-- 这一条 SQL，不需要任何外部数据源，不需要任何额外请求
SELECT symbol FROM bar
WHERE day = ?1
  AND abs(close - prev_close) * 10000 / prev_close > 1100;   -- 涨跌超过 ±11%
```

命中就说明：要么是除权（真的发生了公司行为），要么是数据错位。

- 命中后**不阻塞**，不告警，不进质量表
- 只在"个股详情"页画 K 线时，**跳空处画一段虚线**而不是实线
- 这样你看到的曲线不会因为一根假暴跌而失真

一条 SQL，一个字段，零额外请求。这个我强烈建议留着——它不是"自检系统"，
它只是**把包里已经有的字段存下来，顺手算一下**。

如果你连这个也不要，说一声，我删掉。

## 7. 自进化（V3 的招牌，也是最容易做假的地方）

### 7.1 把"进化"拆成四个独立、可验证的能力

| 能力 | 是什么 | 不是什么 |
| --- | --- | --- |
| **A. 策略库** | 多个策略可注册、可并存、可版本化 | 不是"多写几个 if" |
| **B. 影子验证** | 候选策略真跑、真记账、但不占资金不下单 | 不是"跑个回测就算" |
| **C. 治理晋升** | 达标才能进实盘槽位，有硬阈值和证据链 | 不是"回测收益高就上" |
| **D. 参数进化** | 在**冻结的**搜索空间内找参数，且必须 walk-forward | 不是"全历史最优化" |

**没有 B 的 C 是自欺欺人**。这是最关键的一条：任何"直接从回测晋升到实盘"的设计都会过拟合。
影子期必须真实经历时间流逝（每天累积、不能补算）。

### 7.2 状态机

```
   draft ──┐
           ▼
        candidate ──(OOS 达标)──▶ shadow ──(shadow 达标 + 边际)──▶ active
           ▲                       │                              │
           │                       │                              │
           └───(回滚)──────────────┴──────(回撤超限)──────────────┘
                                                              ▼
                                                          retired
```

每一步的准入条件写死在 `evolution.rs` 的 `EvolutionPolicy` 里，**配置可改但必须有记录**。

### 7.3 晋升评审的输出必须是人能看懂的

```json
{
  "candidate": "low_vol_value_v3",
  "incumbent": "steady_v1",
  "decision": "reject",
  "checked": {
    "out_of_sample_days": {"value": 34, "min": 20, "pass": true},
    "shadow_days":        {"value": 7,  "min": 10, "pass": false},
    "trades":             {"value": 41, "min": 10, "pass": true},
    "drawdown_bps":       {"value": 820, "max": 1500, "pass": true},
    "margin_bps":         {"value": 63, "min": 50, "pass": true}
  },
  "reason": "shadow 期仅 7 个交易日，距门槛还差 3 天",
  "eligible_on": "2026-11-18"
}
```

**"差多少"必须明确**，否则用户看到就是一句"不通过"，等于没做。

### 7.4 参数进化：怎么做不变成过拟合机器

- 搜索空间**写死并冻结**（比如 8 个参数、每个 5 档，实际用随机采样 200 组）
- **walk-forward**：用前 60% 数据选参，后 40% 验证；只有验证段也好的才留
- **多市场状态**：牛市/熊市/震荡各留一段做验证
- 最终只保留**参数平原**（邻近参数也好）而不是**参数尖峰**（只有这一组好）

这几条起来，工作量不小，但这是"自主进化"和"随机搜索"的分界线。

### 7.5 因子挖掘（用户要求做，排在最后）

**先说清工作量**：这不是"加个功能"，是从零建一条研究流水线。

| 组件 | 工作量 | 说明 |
| --- | --- | --- |
| 因子表达式引擎 | ~1 周 | `Ref($close,1)/$close-1` 这种 DSL，可序列化可缓存 |
| 因子评估 | ~1 周 | IC/IR、分层回测、换手率、衰减曲线 |
| 搜索算法 | ~2 周 | 遗传规划 / 符号回归，要防表达式膨胀 |
| 防过拟合框架 | ~1 周+ | walk-forward、参数平原检测、多重检验校正 |
| **合计** | **4-6 周** | 这是"能用"的下限 |

#### 7.5.1 为什么必须排在 P5

因子挖掘是**放大器**：

- 数据层还在用错误价格 → 挖出来的因子全是噪音
- 回测框架还有未来函数 → 挖出来的因子全是幻觉
- 没有 walk-forward → 挖出来的因子只是历史拟合

**先有可信的地基，再谈挖矿。** 这不是保守，这是避免白干 4 周。

#### 7.5.2 设计要点

**表达式引擎**（借 qlib 语法，但不引入 qlib）：

```rust
// 因子定义就是一段可序列化的字符串
"Ref($close,1)/$close-1"                    // 动量
"Std($close,20)/Mean($close,20)"            // 波动率
"Rank($volume)/Rank($amount)"               // 量额背离
"($high-$low)/$close"                       // 振幅
```

好处：因子可存 DB、可版本化、可对比、可缓存中间结果。

**初始因子库**：直接用 qlib 的 `Alpha158` 清单（158 个已验证的 A 股因子），
不用自己想。这是最大的一块白捡。

**搜索算法**：遗传规划（GP）优于随机搜索，因为它能组合已有因子产生新因子。
必须设**复杂度惩罚**（表达式长度、嵌套深度），否则会挖出
`RANK(REF(...))` 套 10 层的怪物，回测完美、实盘报废。

**防过拟合（最关键）**：
- 每个候选因子必须在 **样本外** 也有效
- 同时报告 **IC、ICIR、分层回测、换手率**，不接受单一指标
- **多重检验校正**：挖 1000 个因子，必然有几个"显著"是运气。用 Bonferroni 或 FDR 控制
- 挖出的因子必须先进 shadow，走第 7.2 节的状态机，不能直接上

#### 7.5.3 一个诚实的预期

**因子挖掘大概率挖不出稳定盈利的因子。** 这是公开研究的基本结论——
A 股日频公开因子的 alpha 早被套利完了。

那为什么还做？三个实际价值：

1. **排除伪因子**：能证明"这个想法没用"，省下以后瞎试的时间
2. **建立评估能力**：有了这条流水线，任何新想法 10 分钟就能得到诚实评估
3. **组合价值**：单个因子弱，但多个低相关因子组合可能有效

如果目标是"系统能挣钱"，因子挖掘的边际贡献**远小于**这三件事：
选对标的池、控制好回撤、别让费用吃掉利润。

## 8. 性能设计（"快速响应"落到实处）

| 场景 | 手段 | 目标 |
| --- | --- | --- |
| HTTP 请求 | 连接池（`deadpool-sqlite`）+ 只读查询走 WAL 快照 | p99 < 50ms |
| 全市场截面查询 | `(day)` 索引 + 只 SELECT 需要的列 | < 10ms |

**一个反直觉的点**：全市场 250 日收盘价矩阵只有 **10MB**。所以"回测慢"从来不是内存问题，
是架构问题（现在是一次一个 HTTP 请求算一只股票）。

## 8.5 盘中预警（3 分钟扫描）

### 8.5.1 实测数据（2026-11-11 本地验证）

| 测试 | 结果 |
| --- | --- |
| 腾讯实时批量 `qt.gtimg.cn/q=`，5 只 | 0.17s |
| 800 只（单请求上限附近） | 0.23s |
| 连续 7 批 = 5600 个代码槽位 | **1.24s**，无限流 |
| 1000 只单请求 | HTTP 414（URL 过长），所以必须分批 |

**结论**：3 分钟扫描一次**毫无压力**，全市场拉一遍 1-2 秒。设计上按 800 只/批分 7 批。

### 8.5.2 定位（必须说清楚）

盘中扫描**只做预警，不做撮合**：

- A 股 T+1，盘中本来就不可能成交
- 免费数据源的分钟数据不可靠，拿它撮合等于自欺欺人
- 所以：盘中告诉你"发生了什么"，成交统一等收盘价

这个定位让整个系统保持简单，同时不丢"反应快"。

### 8.5.3 预警类型

| 类型 | 触发 | 用途 |
| --- | --- | --- |
| 信号预演 | 候选策略在盘中就满足买入条件 | 提前知道今天大概率会买什么 |
| 持仓异动 | 持仓股涨跌幅 > 5% 或跌破成本线 | 提前知道今天会亏还是赚 |
| 触板 | 涨跌停 / 接近涨跌停（>9.5%） | 涨停买不进，得提前知道 |
| 放量 | 当前量 > 前 5 日均量 × 2 | 异动信号 |
| 板块异动 | 所属板块涨幅 > 3% | 轮动机会 |

### 8.5.4 限流保护

腾讯没公开限流规则。3 分钟 × 4 小时 = 80 轮/天 × 7 请求 = 560 请求/天，这个量很安全，
但仍然要有退避：

```
连续 3 轮全部失败 → 间隔 3min 放宽到 6min
连续 5 轮全部失败 → 放宽到 15min，并在页面标"行情源异常"
恢复成功后 10 轮 → 逐级退回 3min
```

### 8.5.5 实现

- Rust 侧 `tokio::spawn` 一个定时任务，只在 9:30-11:30 / 13:00-15:00 运行
- 扫描结果写内存 + 落 `intraday_alert` 表（保留 5 个交易日，自动清理）
- 前端用 SSE 或 15 秒轮询 `/v2/intraday/alerts` 拿最新
- **不写账本，不影响净值，不触发任何成交**

## 11. 已定决策与遗留风险

### 11.1 已定（2026-11-11）

| 议题 | 决定 | 依据 |
| --- | --- | --- |
| 数据校验 | 不做自检系统，看曲线 | 异常在曲线上可见；建系统成本不划算 |
| 盘中 | 3 分钟扫描预警 | 实测全市场 1.24s，无压力 |
| 进化 | 含因子挖掘 | 排在最后，工作量 4-6 周 |
| 验收 | **能挣钱就是好的** | 所有设计围绕"曲线好看且真实" |

### 11.2 关于验收标准"能挣钱就是好的"

这句话作为**最终目标**完全正确——做交易系统不为了挣钱为了什么。但它作为
**过程指标**有个陷阱，必须说清楚：

> 一个系统可以在 20 个交易日里赚钱，纯属运气。
> 如果用它作为唯一判据，你会不断关掉亏钱的策略、留下赚钱的，
> 最后留下来的是一组"过去恰好赚钱"的策略——这叫**幸存者偏差**，
> 下一段时间大概率全线回吐。

**所以曲线要看三件事，不能只看方向**：

| 看什么 | 为什么 | 怎么看 |
| --- | --- | --- |
| **方向** | 赚还是亏 | 总收益率 |
| **波动** | 赚的过程能不能扛住 | 最大回撤、日波动率、夏普 |
| **样本量** | 这点收益是运气还是本事 | 交易笔数、统计显著性 |

一根直线上涨的曲线，如果只有 8 笔交易，那就是运气，不是本事。
**真正好的曲线是"稳步向上 + 回撤可控 + 样本足够"**，不是"涨得最快"。

方案里所有的 shadow 期、最小样本门槛、walk-forward，目的都是**让曲线上的钱是真的**。
否则你优化的不是策略，是历史巧合。

### 11.3 遗留风险（我记在这里，不阻塞实现）

1. **除权未检测** → 假亏损累积，曲线系统性偏低。缓解：6.5 节那条 SQL（强烈建议保留）
2. **单数据源** → 通达信出问题时无人发现。缓解：曲线异常柱 + 手工抽查
3. **8600 无鉴权** → 任何人可创建账户、推进结算。P0 必须修
4. **因子挖掘可能血本无归** → 见 7.5.3，做好心理预期
5. **样本量始终不足** → 65 个交易日、2 只股票，任何统计结论都不可靠
