# 历史资产查询与账本测量

后续执行证据规则使用 policy5，需要新V2文件；本页PIT语义保持。
当前benchmark生成器为ledger-bench-v2，显式提供单向价格与1000000股离线容量。
下文v1及PIT PR中的测量是原固定输入的历史记录，不把变更输入后的耗时当作同一次测量。

## 日终查询语义

`GET /v2/portfolio?asof_day=2026-10-30` 表示指定中国日期（UTC+08:00）
收盘后的日终账本状态：包括该日全部记录，截止下一日零点之前。
`asof_day` 必须为规范的 `YYYY-MM-DD`。同日盘后被拒绝的决策也计入该日计数。
省略参数仍表示当前完整账本，不是按机器时间截断。

Store/query 以已保存的 `SimulationRequest.decision_at` 确定日期，
将其关联的实际 Fill 按账本顺序交给现有 `PortfolioState::apply`，
仅纳入截止日及之前的决策和成交。同一次 SELECT 同时读取决策与成交，
现金、lots、持仓和 `runs_total` 来自一致的 SQLite 读取快照。
拒绝的决策计入 `runs_total`，没有 Fill 就不改变资产；重复提交不产生新记录。
不重新判断成交，不读取最新报价、当前日历或系统时间，也不写任何表。

例如 10 月 30 日买入 800 股、11 月 2 日卖出后，查询 10 月 29 日应无持仓，
查询 10 月 30 日仍有 800 股。随后新增成交不能改写这些历史结果。
`sellable_quantity` 保留现有 T+1 日期记账定义：买入日为 0，后续日期为剩余可用 lot 数量。
它不是该日市场开放或个股允许交易的承诺；周末资产查询不因此获得下单权限。
无成交历史时返回初始现金和空持仓。查询范围外日期也能读取账本，
因为查询资产不需要再次决定该日是否交易；执行的未知日期拒绝规则保持不变。

这是按**决策发生日**重建的固定账本视图，不是“系统在当时实际已经知道什么”的
双时间审计查询。当前不支持历史补单，研究不能通过本接口提交或改写任何事实。
报价的实际接收时间及 offline_fixture 信任等级保持原样。

## 所有权与兼容性

复用 Store/query（唯一职责仍为只读投影与回放），消费者是现有 HTTP 资产接口。
方向仍为 HTTP → Store → Domain；计算委托已有 PortfolioState，API 不复制规则。
不增加业务模块、第三方依赖、表、索引、schema 版本或数据库迁移。
Store 仍是唯一写入权威；submit 和 verify_replay 的交易规则与写入过程没有变化。
Rust/Python/前端依赖及 lockfile 不变；V2 CI 新增 GitHub 官方
`actions/upload-artifact@v4`，仅用于上传测量 JSON 与环境证据。

## 可运行的性能测量

```bash
cd v2
cargo test --locked --all-targets
cargo run --release --locked --example ledger_bench -- 100 1000 5000 > ledger-benchmark.json
```

`examples/ledger_bench.rs` 是测量入口，不是新业务模块或运行时进程。
仅用已有依赖和标准库，通过真实 Store 接口创建离线行情与决策，不直接插入 SQL，
不指定成交数量。固定生成器 ledger-bench-v1、固定 100 分报价、2026 已固定计划交易日：

- 全成交：25 个测试代码，按已知交易日交替买入/卖出，最多 5000 决策/5000 成交。
- 多数拒绝：同一日期代码先买入，然后以新信号身份重复买入；只有第一笔成交。
- 每个规模分别使用全新内存库和临时磁盘库（Store 默认 WAL）。不接触用户数据库。

记录每次 submit 的均值/p50/p95、最初/最后 50 笔、总耗时；
另记行情导入耗时，避免把它混入 submit。查询各测 9 次，完整回放测 3 次。
这些是已热启动、顺序执行的小样本，包含内存分配、SQL/JSON 和磁盘提交，
不包含进程启动/编译；不能外推生产延迟或设为稳定的 CI 性能阈值。
CI 另保存 Rust/Cargo、操作系统、CPU、文件系统资料，与 JSON 一同上传 artifact。
机器缓存、共享 runner 负载和 receipt 时间会变化；确定的是业务输入与预期结果，
不是毫秒耗时或由可信接入端生成的实际 received_at。

每组单独核对成交/决策数、历史前缀不变、现金、重复和冲突后状态、完整回放，
磁盘组还核对关闭重开。事务中途失败的回滚由 Rust Store 测试使用 SQLite trigger 验证，
不能把信号冲突当作中途写入失败的替代测试。没有引入缓存或第二套账本权威。
性能结果和是否需要优化在实际测量完成后记录；本轮不预先实现优化。

## 后续执行真实性的范围

只有历史查询验收后才设计下一条链：证据的价格是否为可执行买卖报价、报价阶段、
买卖价差与可用数量、涨跌停/临时停牌，以及默认全额成交的限制。
先确定独立事实和来源，再设计正常/拒绝/幂等/固定输入回放测试。
本轮不实现完整订单生命周期、多账户、AI 晋级、真实供应商或券商接入。

和磁盘/WAL 时延有噪声，不能拿单次磁盘数字拟合复杂度或宣称容量上限。

5000 笔内的末 50 次约为最初 50 次的 24.5 倍。对照组同样 5000 决策但只有

load_state 逐个解析并应用历史 Fill，证据支持它是随成交增长的主要扩展成本。
这不是 CPU profiler 的逐函数归因，也不表示当前已有用户可感知的性能故障。
当前没有吞吐/延迟目标，因此不以这次微基准决定必须立即优化。

最小后续方案（只建议，本轮未实现）：在现有 Store 内维护可丢弃的最新持仓投影，
启动时由权威 Fill 全量重建；提交在副本上计算，只有 SQLite commit 成功后才替换，
提交失败、冲突和重复均不推进。投影不能接受独立写入、不能成为回放输入；
回放仍从账本完整重建并核对，历史查询仍按截止日投影，不使用最新投影回答历史问题。
不另建表、服务、缓存框架或通用 trait。实施前单独验收收益和内存成本，
实施后必须重跑中途回滚、重试、重开、历史视图和完整回放，再以同一生成器比较。
这些条件当前只定义方案，没有以“提议了缓存”冒充已经完成优化。
