## 3. 公共层应该显性声明什么

不是为了消灭 201 这个数字，而是因为每一次 `X._private()` 都在绕过"输入身份 / 失效条件 / 失败语义"。以下 9 项是**本轮核实到、且消费者 ≥2 个**的缺口；每项给出应当公开的函数面（签名以现有实现为准，不改变语义）。

### P1 数据库连接与写入基础设施 → `paper_storage`

现状：`paper_trading._db`(1490) 19 个访问点、10 个消费者（`api_paper`、`api_settings`、`main`、`demo_seed`、`push_report`、`strategy_service`、`strategy_health_service`、`strategy_retirement_service`、`strategy_retirement_workflow_service`、`strategy_candidate_service`）；`_db_readonly`(1505) 3 点；`_evolution_conn` 1 点；另有 `adaptive_engine._connect` 被 3 个 runner/worker 使用。合计 **27 个访问点、14 个消费者**。

应当公开：`paper_storage.connect()` / `connect_readonly()` / `evolution_connection()`。

障碍（已核实）：`strategy_service.py:145-147`、`strategy_health_service.py:370-371`、`strategy_retirement_service.py:24-25`、`strategy_retirement_workflow_service.py:24-25`、`push_report.py:63-64` 这 5 处是**逐个复制的样板**，不是真的需要主引擎；`test_architecture_boundary_audit` 的私有访问额度是精确值（201，allowance 0），必须先建公开面再改读点，同批登记额度。

### P2 冻结 / 指纹 / 摘要 → 一个 L0 契约

现状：`experiment_contract._digest`(6 点/3 消费者)、`_thaw_json`(5/2)、`_stable_fingerprint`(3/2)、`_freeze_json`(1)、`_normalize_experiment_environment`(1)；`strategy_candidate._SHA256`(7/3)；`shadow_runtime._plain`(27/2)、`_instant`(1)、`_state_for_run`(1)。

这是全仓**最分散的公共能力**：`duplicate_helpers` 里 `_canonical`(29 份)、`_sha`(19)、`_json`(13)、`_thaw`(11)、`_freeze`(11)、`_sha256`(7)、`_loads`(7)、`_digest`(5)、`_canonical_json`(5)、`_content_fingerprint`(5)。

**但不能机械合并**——上一轮 `paper_numeric` 的做法（先建语义矩阵再合并）是唯一正确范式：冻结/摘要面至少存在"历史哈希必须逐字节不变"的约束（`learning_dataset` 的 `FINGERPRINT_VERSION` 就是为此存在）。所以本项的正确交付是：**先写语义矩阵**（输入类型、None/NaN/布尔/无穷、键排序、浮点格式、时区），再把 `experiment_contract` 的五个函数提为公开，`shadow_runtime._plain` 提为公开；`_canonical`/`_sha` 那一批**不在本项内合并**。

### P3 时点解析 → L0 时间契约

`market_data_contract._parse_instant`（6 点）：`market_data_service:114`、`paper_capital_reservations:120,143`、`portfolio_order_intents:36,131`。**资金与预占模块为了解析时点去摸行情契约的私有函数**——这本身就是职责错位：账本不该依赖行情模块。应下沉到 L0（`paper_common` 或独立 `time_contract`），让账本、行情、研究共用同一份时点语义。

### P4 证据引用签发 → `ai_research_contract` 公开面

`_issue_evidence_ref` 被 **6 个 adapter 全部**使用（`ai_research_earnings/news/runtime/strategy/execution/portfolio_adapter`）。6 个 adapter 是同一模式的分片，却都要伸手拿签发函数，说明签发是契约的核心而不是内部实现。

### P5 周期归属只读面 → `paper_order_execution_authority`

`_active_cycle_id_readonly`、`_account_cycle_id_readonly`、`_order_cycle_id_for_order`、`_order_cycle_provenance_for_order`、`_orders_have_cycle_column`、`_assert_order_execution_cycle` 共 7 点，来自 `paper_trading` 与 `paper_lot_ledger`。**"周期归属"是本系统最强的风控不变量之一，却以私有名暴露**——这是最该优先消掉的语义风险（而不是行数最多的）。

### P6 因子时效 → 因子事实 owner

`paper_trading._selection_factor_freshness`(3978-4083, 106 行) 被 `selection_application:321` 使用，`_rebuild_selection_factor_cache`(4127) 被 `history_recovery_runner:47`、`selection_runner:55,103` 使用。这就是上一轮 A7 未完成的那一半：选股应用仍因"因子时效判定"反向依赖交易主引擎。`selection_factor_store`(85 行) 是天然归属。

### P7 账户/策略规格解析：**同名不同语义，必须先统一**

已核实两处实现语义不同：

- `paper_trading._spec_for(account_id, conn=None)`（651-673）：有 `conn` 时用 `SRT.get_context`（**当前周期**，不 pin），无 `conn` 时用 `_user_runtime_context`。
- `paper_risk_service._spec_for(account_id, conn, *, cycle_id)`（118-127）：用 `SRT.get_context_for_cycle`（**周期固定**）。
- 第三处 `strategy_risk_enforcement.effective_spec_for_cycle`(304) 只做"基础 spec × 周期编译画像"的收紧。

三个入口，两种周期语义。当前调用点各自正确，但这属于"同名 helper 不同合同"的典型风险点：任何人把 `paper_trading._spec_for` 用在历史周期路径上，都会静默拿到当前周期画像。**本项建议只做一件事：把两个 `_spec_for` 改名为 `spec_for_current_cycle` / `spec_for_pinned_cycle`，并加守卫断言风险路径必须用 pinned 版本。** 不改逻辑。

### P8 行情取数与来源证据 → 窄的行情应用能力

`paper_trading._quotes`(5837-6133, 297 行) 作为依赖被 `manual_orders` 使用；`data_fetcher._sina/_tencent/_eastmoney_realtime_feed` 被 `quote_probe:28-30` 直接取私有工厂；`data_fetcher._full_snapshot_payload_is_complete` 被 `market_data_service:138` 使用；`data_fetcher._fetch_sina_realtime_for_codes` 被 `paper_trading:6676` 使用。

这里的问题不是"要合并"，而是**取数入口太多、私有工厂被绕开**。公开面应当只有"给 codes + 业务日 + 用途，返回行情与来源证据"一个入口，其余都是内部。

### P9 决策快照 → `paper_decision_audit` 公开面

`_snapshot_date` / `_snapshot_first` / `_snapshot_kline` / `_snapshot_factor_evidence` 4 点全部来自 `paper_trading:1247-1250`（对应新行号见 §5.1），而 `paper_decision_audit` 自己有 `build_decision_snapshot`(264 行)。快照组装是审计域职责，主引擎只应传事实。

### 明确不该动的"公共层候选"

## 5. 重复计算与重复实现（已复现 / 已核实）

### 5.1 学习评价重复构建数据集 —— **已实测 2×，且它是正确性问题而非性能问题**

源码形状（`ee9e604`）：

```
learning_evaluation._evaluate:1829   dataset_status = LD.contract_status(conn, cutoff=..., max_evidence_rows=...)
learning_dataset.contract_status:1869    build = build_dataset(conn, cutoff=..., persist=False)   ← 构建 #1
learning_evaluation._evaluate:1845   dataset = LD.build_dataset(conn, cutoff=..., persist=False)    ← 构建 #2
```

**插桩实测**（内存 SQLite，160 samples / 156 returns，复用仓库自带 `test_learning_evaluation.open_db/seed_panel`）：

| 消费者 | `build_dataset` 次数 |
|---|---:|
| `LD.contract_status` 单独 | 1 |
| `LE._evaluate` / `LE.evaluate_dataset` / `LE.contract_status` | **2** |
| `neural_shadow.readiness` | **3**（两次 cap 不同：40000 vs None） |
| `run_learning_cycle` alpha 路径 | **1（已正确，勿改）** |

两次构建产出的 fingerprint **完全相同**（40 次采样全部 `24e089492185c76e...`，`eligible_rows` 恒为 148）——第二次是纯浪费，不是"换个视角算"。

成本实测（20 次平均）：单次 `build_dataset` 约 26–36 ms，`evaluate_dataset` 约 64–71 ms，冗余那次约占整次评估 **40–50%**（随证据行数线性放大）。**这是夹具级测量，不是生产耗时。**

**比性能更严重的发现（已核实）**：`learning_dataset._evidence_read_snapshot`(1588–1598) 的 `SAVEPOINT` 在 `build_dataset` 内部 `RELEASE`，实测 WAL 下 `RELEASE` 后 `in_transaction` 回到 `False`。即**两次构建之间不持有任何读快照**——今天存在"门禁放行的数据集"与"实际评估的数据集"来自两个不同快照的可能。这不是重复计算，而是并发写下的**正确性漏洞**；单次构建同时消除两者。

另有一处文档与实现不一致：`learning_dataset.contract_status:1822` 的 docstring 自称 *"Lightweight, side-effect-free dataset gate"*，实际在 1869 行执行完整 `build_dataset`。所有把它当轻量探活的消费者（健康页、就绪检查）都在付完整构建成本，并按"轻量"做出错误假设。

建议接口（不改现有返回形状）：

```python
# learning_dataset 内部：一次构建 + 门禁事实
def prepare_for_evaluation(conn, *, cutoff=None, split_spec=None, max_evidence_rows=None):
    """返回 (status_dict, DatasetBuild | None)。门禁失败时 build 为 None 且保留原 blockers。"""

def contract_status(conn, *, cutoff=None, split_spec=None, max_evidence_rows=None) -> dict:
    status, _ = prepare_for_evaluation(...)
    return status          # 对外形状完全不变
```

`learning_evaluation._evaluate` 改用 `prepare_for_evaluation`，门禁通过时消费同一个 build。

验收矩阵（9 项，均可写成单元用例）：

| # | 用例 | 断言 |
|---|---|---|
| 1 | `evaluate_dataset` / `_evaluate` / `LE.contract_status` | `LD.build_dataset` 各被调 **1** 次 |
| 2 | 门禁产出复用 | `build_evaluation` 收到的对象 `is` 门禁产出的 `DatasetBuild` |
| 3 | 指纹不变 | 黄金值 `24e089492185c76e...` 逐字节相同 |
| 4 | 门禁阻断 | 构建 ≤1 次，且**不读取**预测证据 |
| 5 | 对外形状 | 新入口第一返回值与旧 `contract_status` 逐键相等 |
| 6 | 快照一致（回归 §5.1 的正确性漏洞） | 门禁后、评估前改动一行证据，结论仍与"单次构建"一致 |
| 7 | `persist=True` | manifest 只 +1 行，且在 savepoint **之外**写（现状即如此，不得包进 `_evidence_read_snapshot`） |
| 8 | `neural_shadow.readiness` | 构建 3→1；`truncated` 语义不变 |

### 10.2 一个必须解释的设计点：路径用晚绑定

第一版实现里 `paper_storage.paper_db()` 自己按 `data_paths` 解析路径，结果 **`test_strategy_service` 从 OK 变成 7 errors + 1 failure**：本仓 88 处测试用 `P.DB_PATH = <tmp>` 把账本指到临时库，公开连接面不跟随，测试就写到了真实账本（`strategy id already exists`）。

所以最终的形状是仓库里已有的 idiom（`bind_default_runner` / `bind_config_connection` / `bind_dependencies` 同款）：**下层暴露绑定钩子，账本 owner 在组装期登记 `lambda: DB_PATH`，调用时才解析**。依赖方向仍是 L0 ← L4 注册，没有反向 import。代价是 `import_side_effects` 24 → 25（仍在上限 25 内）。

这不是绕过问题，而是把"账本路径的归属"讲清楚：**连接怎么开属于存储边界，哪个库是账本属于账本 owner**。

### 11.2 这批差点做砸了：三个必须记住的教训

第一版改完之后全量回归是 **1136 errors**。原因不是逻辑，而是三类"同名不同作用域"：

**教训一：改名 + 别名只解决"引用"，不解决"patch 的绑定"。**
测试用 `mock.patch.object(PT, "_audit")` 注入断言。owner 内部若仍调用 `_audit(...)`
（解析到别名），而消费者调用 `audit(...)`（公开名），patch 只替换别名那个绑定，
消费者路径完全绕过注入——测试仍然"通过"，但测的是没被 mock 的真实函数。
**修法**：owner 模块内部也必须改用公开名，别名只留给外部。这一条影响 30 个模块。

**教训二：公开名会撞上局部变量。**
`_rows` → `rows` 之后，`rows = _rows(conn, ...)` 变成 `rows = rows(conn, ...)`，
`UnboundLocalError`。9 个目标撞名（`rows`/`instant`/`current`/`conditions`/
`constraints`/`account_params`/`scenario_sessions`/`strategy_stamp`/`active_cycle`），
最终给它们换了不撞名的公开名（`query_rows`、`parse_shadow_instant`、
`current_selection`、`account_conditions`、`rule_constraints`、
`load_account_params`、`build_scenario_sessions`、`resolve_strategy_stamp`、
`load_active_cycle`）。
**推断**：这三个词（rows / current / conditions）几乎一定会出现在函数体里，
**私有名带下划线恰好是一种防撞机制**；公开化时必须先做一次 AST 级撞名扫描。

**教训三：批量正则替换会误伤形参和默认值。**
`(,\s*)rows(\s*[,\)])` 这条规则把 `def _round_quote_offer(asof_day, rows)` 的形参
也改成了 `query_rows`，还把 `_num(meta.get("rows"), rows)` 的默认值换成了函数对象。
**修法**：只替换"裸调用 `name(`"，不替换裸引用；形参/默认值/解包目标要单独排除。

### 11.3 哪些是"真改进"，哪些只是"名字变公开"

### 13.3 `_buy_order` 1,195 行为什么不能盲切

报告 §4.1 已经给出 14 个块的行区间，其中标为"纯"的 462 行（D/F/I/J/K）确实可以变成

  的先后决定最终数量。切错一次就是风控行为变化；
- 现有唯一的等价性证据是黄金回放（`test_production_path_golden_replay` 等），它覆盖
  正常路径，但**不覆盖**每个块的边界输入。

正确做法是：**先给 `_buy_order` 建一个逐块的输入/输出快照夹具**（把 14 个块的入参与

**本轮把这一块真的切了一次，并量了结果**（切完通过 `ast.parse` + 导入冒烟，随后回退）：

- 切的是块 D（准入判定，`reasons = []` → `if not dynamic_news["new_entry_allowed"]`），

- 结果：`_buy_order` **1,195 → 1,186（−9）**，而 `paper_trading.py`

也就是说：**最小的一个纯块，抽出来的净效果是函数少 9 行、文件多 32 行**。要走到 `<200`，
需要按这个比例搬掉约 **1,000 行**——那不是"再切几块"，而是把 1,195 行的线性脚本改写成
"协调器 + 8~10 个带显式输入 dataclass 的阶段函数"。每次改写都要先把该阶段的输入/输出
快照钉住，否则风控判定顺序一变就是行为变化。

**所以这一项本会话按计划回退了**：留着它只会让 `max_file_lines` 变差，而 `max_function_lines`
只降 0.75%，不构成任何有意义的进展。度量口径下的"进步"必须是净收益，不是位移。
